# RunQuest 예상 질문과 답변

시연 중 받을 가능성이 높은 질문을 기능, 데이터, 성능, 기술 선택, 한계 관점으로 정리했습니다.

## 프로젝트 개요

### 1. RunQuest는 어떤 문제를 해결하는 서비스인가요?

RunQuest는 러너가 자신의 컨디션, 선호도, 위치, 과거 기록을 바탕으로 오늘 달리기 좋은 코스를 쉽게 찾도록 돕는 서비스입니다. 단순 코스 목록이 아니라 설문, 러닝 기록, 현재 위치, 날씨 정보를 함께 반영해 다음 행동을 추천합니다.

### 2. 기존 러닝 앱과의 차별점은 무엇인가요?

일반 러닝 앱은 기록 저장과 통계에 집중하는 경우가 많습니다. RunQuest는 기록 저장에 더해 코스 추천, GPX 기반 코스 관리, 커뮤니티 게시글 연동, 챗봇 추천, 배지와 출석 같은 동기부여 흐름을 함께 제공합니다.

### 3. 왜 대전 지역 중심으로 구현했나요?

시연과 검증 가능한 범위를 명확히 하기 위해 대전 지역으로 제한했습니다. 코스 좌표와 GPX 데이터를 직접 검수할 수 있고, Kakao Map에서 실제 경로가 올바르게 표시되는지 확인하기 쉽기 때문입니다.

### 4. 사용자는 어떤 흐름으로 서비스를 이용하나요?

사용자는 회원가입 후 설문을 완료하고 추천 코스를 확인합니다. 코스를 선택해 GPS 또는 시뮬레이션 모드로 러닝을 시작하고, 완료 후 기록과 피드백을 확인합니다. 자유 러닝으로 만든 경로는 내 코스로 저장해 이후 게시글 작성에도 연결할 수 있습니다.

## 추천 기능

### 5. 코스 추천은 어떤 기준으로 동작하나요?

추천은 설문 점수, 최근 러닝 기록, 현재 위치, 복귀 여부, 안전 보정 값을 조합해 계산합니다. 위치 권한이 있으면 코스 시작점과의 거리를 크게 반영하고, 기록이 쌓일수록 사용자의 실제 러닝 성향 비중을 높입니다.

### 6. 신규 사용자와 기존 사용자의 추천 방식은 어떻게 다른가요?

신규 사용자는 기록이 부족하므로 설문 결과를 중심으로 추천합니다. 기존 사용자는 최근 기록의 거리, 페이스, 선호 코스 유형을 함께 반영합니다. 오랫동안 기록이 없는 복귀 사용자는 무리한 코스를 피하도록 안전 보정 비중을 둡니다.

### 7. 추천 알고리즘을 AI라고 설명할 수 있나요?

핵심 코스 랭킹은 설명 가능한 규칙 기반 점수화 방식입니다. 생성형 AI는 챗봇 응답, 추천 이유 설명, 러닝 피드백 문구 생성에 보조적으로 사용됩니다. 외부 AI 호출이 실패해도 로컬 fallback으로 서비스 흐름은 유지됩니다.

## 러닝 기능

### 8. GPS 러닝과 시뮬레이션 러닝은 어떻게 다른가요?

GPS 러닝은 브라우저의 `navigator.geolocation.watchPosition`으로 실제 위치를 추적합니다. 시뮬레이션 러닝은 선택한 코스의 route point를 시간에 따라 보간해 이동하는 방식입니다. 시뮬레이션은 시연용이며 실제 위치 권한 없이도 흐름을 보여주기 위해 사용합니다.

### 9. GPS가 꺼져 있거나 권한이 없으면 어떻게 되나요?

GPS 권한이 없으면 실시간 위치 추적은 동작하지 않습니다. 사용자는 시뮬레이션 모드로 러닝 흐름을 확인할 수 있습니다. 실제 배포 환경에서는 GPS가 HTTPS 보안 컨텍스트에서만 안정적으로 동작하므로 HTTPS 배포가 필요합니다.

### 10. 일정 거리 미만의 기록은 왜 저장하지 않나요?

실수로 시작했다가 바로 종료한 기록이나 GPS 오차로 생기는 의미 없는 기록을 방지하기 위해 최소 100m 이상 이동한 러닝만 저장하도록 했습니다. 기준 미만이면 기록을 삭제하고 사용자에게 안내합니다.

### 11. 자유 러닝 완료 후 코스로 저장할 수 있나요?

가능합니다. 기본 DB 코스가 아닌 자유 러닝에서 track point가 충분히 쌓이면 완료 페이지에서 해당 경로를 사용자 코스로 저장할 수 있습니다. 저장된 코스는 내 코스 목록과 커뮤니티 게시글 작성 흐름에 연결됩니다.

## 데이터와 DB

### 12. 주요 엔티티는 무엇인가요?

주요 엔티티는 사용자, 프로필, 설정, 설문 응답, 기본 코스, 사용자 코스, 러닝 기록, 출석, 배지, 알림, 커뮤니티 게시글, 댓글, 좋아요, 저장 게시글, 챗봇 세션, 추천 세션입니다. 상세 관계는 `docs/ERD.md`에 정리되어 있습니다.

### 13. GPX 기반 코스 데이터는 어떻게 만들었나요?

사용자가 제공한 GPX 파일을 파싱해 route point, 거리, 고도 상승량, 시작 좌표를 계산했습니다. 경로가 없는 기존 코스는 삭제하고, 검증 가능한 GPX 코스만 fixture와 DB에 반영했습니다.

### 14. 코스 삭제 시 기존 기록이나 게시글은 어떻게 보호되나요?

코스와 연결된 러닝 기록, 게시글은 `SET_NULL` 정책을 사용합니다. 따라서 코스가 삭제되어도 기록과 게시글 자체는 사라지지 않고, 연결 코스 값만 비워집니다.

### 15. 0km 러닝 기록은 왜 삭제했나요?

0km 기록은 실제 러닝 성과와 추천 알고리즘을 왜곡할 수 있습니다. 통계, 출석, 추천 가중치가 더 정확해지도록 기존 0km 기록을 정리했고, 새 기록도 최소 거리 조건을 통과해야 저장됩니다.

## 커뮤니티와 성능

### 16. 커뮤니티 목록이 느렸던 원인은 무엇인가요?

목록 응답에 상세 코스, 러닝 기록, 댓글, base64 이미지 같은 무거운 데이터가 함께 포함되어 있었습니다. 이 때문에 응답 크기와 쿼리 수가 불필요하게 커졌습니다.

### 17. 어떤 방식으로 커뮤니티 페이지를 최적화했나요?

목록 API에서는 이미지 원본과 상세 nested 데이터를 제외하고, 좋아요 수와 댓글 수는 annotation으로 계산했습니다. `select_related`, `prefetch_related`, `defer`, DB index를 적용해 목록 API를 1 query 수준으로 줄였습니다.

### 18. 성능 로그는 어떻게 확인하나요?

`.env`에 `RUNQUEST_PERFORMANCE_LOGS=True`를 설정하면 요청별 실행 시간과 쿼리 수가 `backend/runquest-performance.log`에 기록됩니다. 함수 단위 측정은 `time_block` 유틸리티로 남깁니다.

### 19. 현재 측정 결과는 어떤가요?

로컬 DB 기준 커뮤니티 최신 목록은 약 200ms / 1 query, 인기 목록은 약 15ms / 1 query, 상세 조회는 약 11ms / 2 queries 수준으로 측정되었습니다. 챗봇 로컬 응답은 약 31ms 수준입니다.

## 기술 선택

### 20. 왜 Django REST Framework와 Vue를 사용했나요?

DRF는 인증, 직렬화, 권한, API 문서화에 강점이 있고, Vue는 SPA 화면 구성과 상태 관리가 가볍습니다. 백엔드와 프론트엔드를 명확히 분리해 REST API 기반 구조를 만들기 적합했습니다.

### 21. Pinia는 어떤 역할을 하나요?

Pinia는 인증 상태, 코스, 러닝, 추천, 커뮤니티, 챗봇, 알림 같은 프론트엔드 상태를 관리합니다. 화면 간 이동 중에도 필요한 데이터를 유지하고 API 호출 로직을 분리하는 데 사용했습니다.

### 22. JWT 인증 흐름은 어떻게 구성되어 있나요?

로그인 시 access token과 refresh token을 발급합니다. 프론트엔드 Axios 클라이언트가 access token을 `Authorization` 헤더에 담아 요청하고, 만료 시 refresh token으로 갱신합니다.

### 23. Kakao Map 연동에서 주의할 점은 무엇인가요?

Kakao Map JavaScript SDK 키가 필요하며, 배포 도메인을 Kakao Developers Web 플랫폼에 등록해야 합니다. 지도 표시 좌표는 위도/경도 순서와 Kakao Map의 LatLng 입력 순서를 혼동하지 않도록 주의해야 합니다.

## 한계와 개선 방향

### 24. 현재 프로젝트의 가장 큰 한계는 무엇인가요?

실제 모바일 GPS 환경에서 장시간 검증이 충분하지 않고, 이미지는 아직 운영용 파일 저장소 방식이 아니라 base64 JSON 기반 흐름이 남아 있습니다. 또한 로컬 SQLite 기준으로 최적화되어 있어 운영 규모에서는 PostgreSQL 전환이 필요합니다.

### 25. 이미지 업로드는 어떻게 개선할 수 있나요?

게시글 이미지 원본을 DB JSON에 저장하는 대신, Django media 또는 S3 같은 오브젝트 스토리지에 저장하고 URL만 DB에 보관하는 방식으로 바꾸는 것이 좋습니다. 목록에는 썸네일 URL만 제공하면 응답 크기를 더 줄일 수 있습니다.

### 26. 추천 알고리즘은 어떻게 고도화할 수 있나요?

현재는 설명 가능한 점수 기반 방식입니다. 이후에는 사용자 행동 로그, 코스 완주율, 북마크, 게시글 반응을 추가해 개인화 가중치를 더 정교하게 만들 수 있습니다. 충분한 데이터가 쌓이면 협업 필터링이나 임베딩 기반 추천도 고려할 수 있습니다.

### 27. 운영 DB로 전환하려면 무엇이 필요한가요?

PostgreSQL 설정, 환경 변수 분리, 마이그레이션 검증, 인덱스 재확인, media/static 파일 처리, HTTPS 배포, CORS/Allowed Hosts 설정이 필요합니다. 배포 후에는 실제 요청 로그를 기준으로 느린 쿼리를 다시 점검해야 합니다.
